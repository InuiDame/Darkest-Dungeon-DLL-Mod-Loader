# 执行预算按真实时间，防住意外，不承诺挡住刻意构造的卡顿

每次从 C++ 进入 Lua（`main.lua`、事件回调、定时器、协程恢复、拆除和重载时的 `<close>`）是一个入口，按真实时间（QPC）计预算，默认 50 毫秒，`main.lua` 500 毫秒。超出后报错，并且粘滞到回到 DDLua 为止，Mod 用 `pcall`、`xpcall`、协程都吞不掉。超预算的回调直接停用，`main.lua` 加载失败，协程终止。超时由计数 hook、库函数长循环里的进度检查、没有 `lua_State` 的内核操作之后的检查、大分配前的检查和入口结束时的检查发现（Lua 补丁见 [ADR 0019](0019-lua-as-cpp-with-patches.md)）。紧急 GC 和原子阶段这类整段停顿和当前入口无关，计时后补到它的截止时间上，每个入口最多补一份预算或一次停顿，GC 阈值压在内存上限以下，让大堆也走增量 GC。

预算的目标是：Mod 的死循环、失控的递归、意外的大数据量不会卡死游戏，一个 Mod 出问题不会连累别的 Mod。它**不承诺**挡住刻意构造的卡顿：一次不能中途打断的操作（字符串转数字、长串比较、内存复制）超出的幅度最多是一次操作；GC 停顿发生时游戏照样卡这一下；一帧里事件回调的总时间没有上限；哈希密钥不是密码学强度；原生代码的耗时不计入。完整的「能保证」「不能保证」清单和实测数据在 `docs/03-lua-system.md` 的「沙箱和稳定性」。

脚本 Mod 的安全底线是 [ADR 0014](0014-sandbox-no-raw-memory.md) 的沙箱：碰不到内存、文件、进程。预算是稳定性措施，不是安全边界。

## 考虑过的方案

- 只数指令：和卡顿的时间没有对应关系，也数不到 C 函数里的循环。
- 一帧的总预算覆盖事件回调：预算用完以后剩下的回调只能跳过，事件语义就不对了。调度器的工作可以顺延，所以只给它设每帧总量（`frame_budget_ms`）。
- 把 GC 的时间整个从入口里扣除：分配密集的 Mod 就能按比例超出预算；有效的紧急 GC 次数不封顶时又回到卡死。
- 继续逐个排查所有可能的慢路径：三轮对抗审核都在同一类问题上挖出新的阻断，这一类没有终点。修法改成结构性的（带密钥的哈希、追踪正在运行的线程、入口结束时检查），剩下的作为已知限制写进文档。

## 后果

入口结束时的检查和真实时间计时，会把和 Mod 无关的停顿（线程被抢占、同步写日志被杀毒软件卡住）也算进当时的入口。玩家装了恶意的 Lua Mod，最坏是游戏偶尔卡顿，卸载即可。要更强的隔离，只能把 Lua 放到单独的线程或进程，这和「所有回调在主线程」（[ADR 0009](0009-off-thread-events-deferred.md)）冲突，不在计划内。
