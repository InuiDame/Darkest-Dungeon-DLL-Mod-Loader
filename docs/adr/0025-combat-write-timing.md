# 写操作在安全点立即执行，事件回调里排队，规则回调里拒绝

buff 增删、施加 effect、注册 buff 和 effect 定义这些写操作，只在主线程、存档里、不在加载中（三条加载线程运行的状态）、不在 PvP 对局中执行，否则拒绝并给出原因。满足这些条件之后，按调用时所处的位置分三种：

- **安全点**立即执行，同步返回结果（组 guid、删掉的条数、加上的条数）。安全点是：DDCore 正在执行帧边界的逻辑（`UpdateStateInternal` 的 detour 里执行 `OnFrameBody` 期间），事件中枢的派发深度为 0，DDCore 自己没有在调用游戏函数。lifecycle 回调、task 任务、操作回调都是安全点，所以 DDLua 的 `main.lua`、定时器、协程、`done` 回调也是。
- **事件回调里**（原生事件、语义 hook 的派发，包括立即执行的写操作同步派发的 `buff.add`/`buff.remove`）排进队列，返回操作号。下一个帧边界按入队顺序执行，执行前重新解析句柄、重新判断时机，结果经插件注册的操作回调送达（DDLua 转成 `opts.done`）。每个插件最多排 256 个，DDLua 再按 Mod 分，每个 Mod 128 个；退出存档时还没执行的以「已取消」通知。
- **规则回调里**一律拒绝（`DD_COMBAT_E_IN_RULE`），不排队。

读接口（buff 表、Buff 库、effect 表）另有一条：只在主线程、没有加载线程在跑时可读，否则返回失败。`read_ready` 告诉插件这是「加载中，暂时读不到」，DDLua 据此返回以「加载中」开头的原因。

依据见 `knowledge/dd1/combat.md` 的「Buff 表的指针失效」：游戏在持有 buff 表内指针时调出去的地方很多（刷新时缓存 first 再判定规则、`479BA0` 的结果列表、`5C46D0` 遍历中调用谓词），P4 探针场景里一半的添加让表重新分配；`load_raid`、`load_town` 线程会前移、搬动 buff 表，重建 Buff 库和 effect 表，主线程这时照常跑定时器和延迟事件。帧边界上游戏不持有这些指针。

## 考虑过的方案

- 所有写操作都排队：Lua 在 `main.lua`、定时器里也拿不到 guid，脚本 Buff 的初始状态要等一帧才能绑定，简单的写法都得改成回调。
- 事件回调里也立即执行：回调可能正处在 buff 表的遍历中（`buff.remove` 在 `5C46D0` 的遍历里，规则判定在 `479BA0` 里），增删会让游戏读到释放的内存或漏判条目。
- 规则回调里排队：规则判定非常频繁（探针约 22 分钟 114 万次），回调里写一次就是每次判定排一个。规则应当只读。
- 用上一帧的 `System::Loading()` 判断加载中：`CampaignLoad` 那一帧会被误判，读档后马上做的初始化全被拒绝。改用当时的状态机（last == next 且是三个加载状态之一）。

## 后果

- 事件回调里的写操作至少晚一帧生效，调用方用操作号（DDLua 的 `done`）对上结果；脚本 Buff 靠它把状态绑到排队添加得到的 guid 上。
- 立即执行会同步派发 `buff.add`/`buff.remove`，形成嵌套的 Lua 入口。DDLua 把嵌套入口隔离计时（保存、恢复外层的截止时间、粘滞标记和补偿计数，按自己的预算重新计时），嵌套用掉的时间补给外层，每个外层入口最多补 max(一份预算, 最长的一次嵌套)，规则和 [ADR 0020](0020-lua-budget-best-effort.md) 的 GC 停顿补偿相同。写操作的 C 函数返回前检查一次截止时间；嵌套回调里出原生异常时，外层入口也交给它自己的隔离（`AfterReentry`）。
- 加载画面期间 Lua 的读接口拿到「加载中」，Mod 要等加载结束再读，不能把这时的 `nil` 当成「条目没了」。
- PvP 的拒绝沿用 [ADR 0011](0011-pvp-no-mutating-dispatch.md)。
