# 存档旁路按内容哈希核对，不一致时不给数据

插件在 `Load` 里声明使用持久化（DDLua 总是声明），每次游戏存档时交出自己的数据（字节串），DDCore 把它写进存档旁边的旁路；读档时核对旁路和游戏存档是不是同一时刻的，一致才交回。

- **位置**：`<游戏根目录>\DDModLoader\save\<账号>\<设备>\<插件名>\<key>.ddsave`，保留上一代 `.prev`。账号是 SteamID32（离线版、取不到时是 `local`），设备是当前 profile（槽 5 的设备名，`steam_profile_N` 或 `profile_N`）。DDLua 每个 Lua Mod 一个 key（`dd.store` 和脚本 Buff 状态），DDCore 自己的标签表是 `DDCore\tags.ddsave`。不放进 Steam 的 profile 目录，不影响云存档。
- **一致性**：观察 hook 按（设备，文件名）记每个 `persist.*.json` 最后一次写入和读取的内容哈希（FNV-1a 64）和大小（同名文件会写到 `steam_profile_N` 和联机的 `steam_profile_9` 两个设备）。写旁路时文件头记下这一刻的名册哈希，在地牢里再加 raid；读档时只比较名册，在地牢里再加 raid：当前一代一致是 `loaded`，否则上一代一致是 `prev`，都不一致（或文件损坏）是 `mismatch`，没有旁路是 `empty`，判断不了是 `unavailable`。不一致时不给数据、不自动修复，原来的两代在第一次写之前改名留底（`.mismatch-<时间>`，每种留 2 份）。新战役复用旧存档位（读到的名册和 `scripts\starting_save` 里的相同）时是 `empty`，旧旁路改名为 `.oldcampaign-<时间>`。
- **时机**：游戏在当前 profile 上写了任何 `persist.*.json` 之后，下一个帧边界（没有加载线程在跑时）派发 `campaign.save`，只读；所有订阅之后按插件加载顺序调用各插件的 `on_save`，DDLua 这时取快照。依据是探针 0B-13：主线程写存档到下一个帧边界之间没有 buff 增删、持续时间结算、技能执行，帧边界的状态和刚写的存档对应。快照在主线程取，写盘在后台线程：同一个文件的连续写入合并，写 `.tmp`、`FlushFileBuffers`、`ReplaceFileW`，失败按退避重试；退出存档时等 3 秒、退到桌面时等 10 秒。
- **地牢里的存档**：游戏在 `CampaignLoad` 之前（状态 1 的 `3DBC20`）就读过一次 raid，DDCore 读档时按名册和 raid 一起判断两代。数据在 `main.lua` 之前交出，`as_raid_start` 加载结束后再拿 `load_raid` 读到的 raid 确认一次，之后才恢复怪物的标签和脚本 Buff 状态；二次确认不一致时这次进存档不再写这个 key，免得把不一致那一代的数据按新哈希写回去。
- **观察 hook 常驻**：有插件声明时，AppReady 装 4 个内联 hook（`2487E0` 排队写文件、`248D60` 读文件、`2923A0` 选槽复制 backup、`3D1CC0` 退到桌面），之后不拆。它们只读内存、算哈希、加锁记录，不改游戏行为。存档的读取早于 `CampaignLoad`，按需安装赶不上。这是 [ADR 0007](0007-hooks-on-demand.md)「按需安装」的例外：DDLua 存在时，即使没有 Lua Mod，hook 报告也是 1 + 4 个目标。

## 考虑过的方案

- 比较存档里的时间戳、`totalelapsed`：只精确到秒，很多写入不更新头信息，标识不了某一次写入。
- 在 `2487E0` 里同步派发：同一调用链接连写几个文件，要判断什么时候一组写完。帧边界派发更简单，探针证明这时的 Lua 状态和刚写的存档对应。
- hook `60D610` 判断「探索存档这一组写完」：主线程上的一组在同一帧里写完，加载线程上的等加载结束，少一个 hook。
- 一致性比较 `persist.game.json`：读城镇存档时 `load_campaign` 线程会重写它。
- 只在写名册或 raid 时派发（第一版）：城镇里升级建筑、城镇事件只写庄园、城镇文件，之后改的 Lua 状态进不了旁路（审核 B-S4）。
- 不一致时自动选一代，或者照常写：云同步来的存档、旁路落后一次都会让读档不一致，自动修复会让 Mod 拿到别的时刻的数据；照常写两次就把原来的两代挤掉了（审核 B-S3）。
- 按需安装观察 hook：`CampaignLoad` 时名册早就读完了。
- 当前 profile 用 `App+1`：前端选槽复制 backup 时它还没更新。

## 后果

- 取代 [ADR 0021](0021-lua-vm-per-campaign.md) 的「切换存档时脚本状态全部丢失」：VM 仍然按存档新建，`dd.store` 和脚本 Buff 的状态经旁路随存档保存。P3 的「没有 Lua Mod 时 hook 报告 1 个目标」改成 1 + 4（`tools/p3_scenario_check.py` 的 #7 和 09 已改）。
- 旁路和游戏文件之间没有事务，崩溃落在两边写入之间时读档判成不一致；游戏自己写盘不是原子的，这超出旁路的能力。
- 读档不一致时 Mod 从空表开始，原来的数据只能手动找回（改名留底的文件）；raid 二次确认不一致时已经交出的 `dd.store` 收不回来，也没有专门的通知，只能看 `dd.store_status()`。
- `battle_snapshots` 里没打完的其他战斗、备用名册上的英雄，状态和标签不保存。
- 栈上传的窄参数要按真实宽度读：`2487E0` 的大小、`248D60` 的容量和返回值是 32 位。第一版按 64 位读，每次写入都被当成太大而跳过（P4 审核 B 的阻断 B1），主菜单自检看不出来。
