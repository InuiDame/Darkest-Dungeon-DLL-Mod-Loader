# Actor 句柄是不带指针的值

`DDActorRef` 由类型、id、存档序号、探索序号、战斗序号和名册组成，不保存原生指针，每次访问都重新解析：英雄按 hero id 在记录下来的那个名册（主名册或备用名册）里找，怪物按 guid 在当前战斗的怪物表里找。全部字段相等才是同一个 actor。跨存档、跨探索、跨战斗的旧句柄解析失败，不会指到别的对象。

- 怪物 guid 每场战斗重新计数（`Battle::Create` 在 `5A40F7` 清零），所以怪物句柄必须带战斗序号。
- 探索序号和战斗序号由 DDCore 在每帧的阶段取样和每次 actor 调用时取样维护，不订阅事件、不装 hook，没有 Lua Mod 时没有任何开销。依据和已知盲区见 `knowledge/dd1/combat.md` 和 `core/src/game/phase_tracker.h`。
- 指针转句柄要求成员关系：英雄必须在名册里，怪物必须在当前战斗的怪物表里，否则不给句柄。阵亡的英雄留在名册里，句柄仍然有效；解雇的英雄被删除，句柄立即失效。
- 只开放偏移核实过的字段（P3 是 HP、最大生命、压力、职业 id），最大生命调用游戏自己的计算函数。

Lua 里同一个 actor 只有一个 userdata（按句柄的值驻留在弱值表里），`==`、`rawequal`、表的键都成立，可以跨回调、跨协程保存。

## 考虑过的方案

- 句柄里保存指针加代数：游戏对象由游戏释放，DDCore 不知道什么时候失效。
- 订阅 `BattleCreatedEvent`、`RaidStartEvent` 维护序号：没有 Lua Mod 时也得注册 listener；第一个怪物句柄就在第一场的 `battle.start` 里创建，按需注册赶不上。
- 用 Battle 对象或 `Raid::Current` 的地址区分战斗、探索：Battle 内嵌在 Raid 里，地址不变；删除和新建可能拿到同一个地址。

## 后果

每次读字段都要扫一遍名册或怪物表（约 100 项）。句柄在游戏还没把对象放进名册或怪物表之前拿不到。
