# 游戏更新走布局清单、基线、校验、修复这条流水线，宁可报需要人工也不给错的结论

[ADR 0006](0006-signature-addressing.md) 只管地址：特征码唯一命中就算成立，`check_sigs.py` 离线校验。结构偏移散落在 C++ 里，变了发现不了；特征码唯一命中的却是别的函数（误绑定）也发现不了；游戏更新后要人工逐条改特征码。U1 把这件事改成一条可验证、可修复的流水线。运行时怎么用同一份清单见 [ADR 0036](0036-runtime-layout-check.md)。

最危险的是两件事：**误绑定**（特征码或依据仍然唯一命中，命中的却是别的函数、别的指令）和**错误修复**（修复工具给出一个看似合理的错地址、错偏移）。它们比「报失效」糟得多，会让 DDCore 读写错位置、损坏存档。下面每条规则都按这个排序取舍：有疑问就报「需要人工」，「没法确认」不算通过。

## 决策

### 清单是唯一来源

- 地址在 `core/src/game/signatures.inc`，其余游戏布局（结构偏移和大小、虚表槽位、枚举表、事件和 Query 负载、命中位置上的固定偏移、函数原型的参数个数、字段宽度）在 `layout.inc`，两个文件合起来是布局清单。加载器、DDCore、`tools/dd_update.py` 都从这里读，C++ 经 `layout.h` 取常量，不再有散落的定义。格式的语义在两个文件开头，U1a 定下之后只加项、不改含义。
- 每一项写明依赖它的服务和主题（`DD_DEPS`、`DD_LAYOUT` 的 deps），校验报告的「失效影响」和运行时停用都按这张表。
- 每一项至少有一种依据：可在运行时求值的 `DD_EVIDENCE`（C++ 和 Python 同义，`tools/ddupdate/evidence.py` 是参考实现）、只能离线求值的 `DD_OFFLINE`（按名字挂到 `offline.py` 的检查），或者明确标成没有静态依据的 `DD_UNVERIFIED` 并写明更新后怎么核实（`test_events` 自检、探针、对照反编译）。
- **组**（`DD_GROUP`，U1 修复 FB，审核 A 的 S4）：一起变的项编成组：同一张虚表的槽位和槽里函数的原型、同一个结构的字段和宽度、一个函数和它的原型。成员可以是清单项或特征码，一个成员可以在几个组里，组要同时有运行时能核对的成员（RUNTIME 项、特征码）和没有运行时依据的成员（NONE、OFFLINE 项）。这个宏只给 Python 用，C++ 展开成空。现在有 44 个组；技能表、事件和 Query 的负载、游戏名字表没有运行时能核对的成员，不编组，accept 时和其他 NONE 项一样逐项确认。

### 基线

- 每个已知版本一份 `tools/baseline/<版本名>.json`：特征码命中的函数的指纹（规范化指令序列、大小、`.pdata` 范围）、调用者和被调用者、引用的字符串和全局、每条指令引用了什么，以及每条依据的命中所在函数和指令下标。U1 修复 FB 加了两样：生成基线时清单项的值（`items`，同组升级拿它和现在的清单比），GLOBAL_ANY 每个命中所在函数的代表（`hit_reps`，按指纹相似度贪心聚类，Steam 版 `EventTypeCount` 69 个命中 3 个代表）。只存规范化 token 和引用，不存机器码（仓库公开）。
- 同一个 exe 两次生成字节一致；改了清单的特征码或依据要重新生成（`dd_update.py baseline`）。游戏更新后旧 exe 通常已被覆盖，修复只靠基线做指令对齐，所以存的是完整指纹而不是摘要。
- 相似度是规范化 token 3-gram 的 Dice 系数，阈值 0.85：同一函数跨版本最低 0.929，大函数的随机对最高 0.361（U1a 报告第 7 节）。完全相同的模板实例指纹区分不了，要靠调用者、调用关系和依据。**这组数据只来自同源的两个构建**（Steam 版和离线版，代码几乎一样），阈值对真实更新的区分力没有数据（见「局限」）。

### 校验：`dd_update.py verify`

对任意 exe 逐项给结论，人读摘要加 JSON，退出码 0 全部通过、1 只有可选项失效、2 必需项失效、有误绑定或无法确认、3 清单或参数有错。

- **特征码**：唯一命中、GLOBAL_ANY 的规则、必需和加载器的 GLOBAL 指向数据节、HOOK 偷取范围在指令边界且不含分支和 rip 相对、偷取不少于 5 字节、函数内没有分支跳进偷取范围、HOOK 的命中位置是函数入口、`DD_ENTRY` 和入口字节一致、和 `knowledge/dd1/hooks.md` 不重叠。原 `check_sigs.py` 的检查全部在内，它和 `check_actor_layout.py` 现在是薄封装。每条问题带类别（`resolve`、`section`、`entry` 是 DDCore 运行时也做的，`static` 只有 verify 做），对照测试和 accept 按它判断运行时会不会自己发现这个失效。
- **同一性**（防特征码误绑定）：命中的函数和基线比较，指纹相似度低于 0.85、基线里有调用者而现在没有、和其他特征码的调用关系一致度低于 0.5、特征码的同一性依据不成立，任何一条都判误绑定。GLOBAL_ANY（U1 修复 FB，审核 A 的 S6）：候选数和基线不同、某个命中所在的函数不像基线里任何一个命中函数代表，都判误绑定；命中次数可以变（模板实例随事件类型增减），只记一笔。只有已知版本才拿自己 SHA1 的基线比，未知版本放一份自己的基线进来不算（否则同一性和位置核对都是自己和自己比）。
- **依据位置**（防依据误绑定，U1d）：依据唯一命中时，命中位置必须落在基线里那条指令经指令对齐映射到的位置；TEXT 范围的依据命中所在的函数要和基线里的是同一个函数；起点是虚表槽的依据，槽里的函数要和基线里的是同一个函数。对不上判误绑定。动机是依据的模式常靠字面量里的邻居偏移区分，结构中间插入字段后，模式可能唯一命中邻居字段的代码，读到的值又恰好等于旧常量；虚表插入槽位后，换进来的函数可能同样满足依据。规则在 `tools/ddupdate/position.py`。
- **没法对照不算通过**（U1 修复 FB，审核 A 的 B1）：依据成立、唯一命中，位置核对却给不出结论（没法对照）时，这一项要有同一项里别的「成立、位置对上」的依据佐证，否则记为**无法确认**，和误绑定一样是退出码 2。唯一的例外是已知版本用自己的基线（这时没法对照只说明基线比清单旧）。审核 A 的反例正是这种情况：`Buff::Instance` 在一串同形状的 int 字段中间插入或删除一个，复制构造里多了或少了一对同形状的复制，第一个受影响字段的依据唯一命中邻居的复制、读到的值等于旧常量，两种对齐方法差一对指令、给出「没法对照」，原来照样判通过。
- **指令对齐**（U1 修复 FB）：以全局序列对齐为准，再分析插入、删除的滑动：空隙两边是重复的 token 时，同样好的对齐不止一种，空隙滑过的旧指令判为「对齐有歧义」；唯一窗口找得到就必须和全局对齐一致，找不到时全局对齐的匹配块不短于 8 条、又没有歧义才采用。一串同形状的复制里多了一对，按 token 本来就分不出多的是哪一对，这时对齐如实给不出结果；这项改进减少的是「周围没有唯一窗口、但对齐其实没有歧义」的没法对照，不替代上一条。
- **布局**：每条依据求值、每个离线检查运行；没有静态依据的项按核实办法分组单列，不算失效。离线检查尽量绑到字段身份上（U1 修复 FB，审核 A 备注 5）：Effect 的字段按解析时的键名（`.chance`、`.dotPoison`……）核对，直接写入的三个字段看前面最近的键名，技能的 effect 列表要求偏移处是一个 vector 的 push_back，`raid_battle_lea` 要求在读 `Raid::Current` 的函数里。
- **同组升级**（S4）：组里有运行时能核对的成员变了（RUNTIME 项失效，或者值和基线生成时不同；特征码失效、误绑定，或者模式和基线生成时不同）时，组里没有运行时依据的成员列进「同组有变化，要人工核实」。不改退出码（这些项本来就核对不了），由 repair 和 accept 处理。
- 每个失效项按依赖表报出受影响的服务和主题。
- 依据本身的求值语义（`evidence.py`）和 C++ 一致，不因为上面这些 Python 独有的检查而改变。C++/Python 对照测试（`cpp_compare.py`）把 HOOK 的静态检查（类别 `static`）、`DD_ENTRY` 比较和依据位置核对单列为「Python 独有的检查」；失效原因里只要有一条是运行时也做的检查、C++ 却判成立，就算不一致（审核 A 的 S5）。

### 修复：`repair`、`--apply`

- `repair --exe <新 exe>` 默认只读，对 verify 失败的项在新 exe 里定位。函数级的定位手段按可信度：放宽特征码（位移、立即数、rel32 写成通配）、从已确认的函数沿调用图传播、字符串和导入和常量锚点、全函数指纹搜索。门槛和区分规则：
  - 相似度不低于 0.85；有调用图约束时满足比例不低于 0.5；基线里有调用者时候选也要有调用者。
  - 第一名要领先其余过门槛的候选 0.10 以上；相近的候选（模板孪生）要靠调用图约束或字符串集合领先 0.5 以上区分，否则报需要人工、列出候选。
  - 可信度「高」要有结构上的支持（放宽特征码命中、调用图约束全部满足、新 exe 里唯一的锚点），只靠指纹或靠调用者区分了孪生的是「中」。
- 重新生成特征码保持原条目的种类和语义（HOOK 从入口开始、偷取字节照旧写通配并给新的 `DD_ENTRY`、偷取范围的安全检查照旧；GLOBAL 重算 capture；CODE 从入口开始），rel32、rip 位移和看起来像地址的值一律通配，扩展到唯一为止，有长度下限，生成后在新 exe 上自检。
- 布局项在修好的特征码上重新求值依据：模式还唯一命中、位置对得上、值变了，就按读到的值反推新值；位置对不上、没法对照或模式不命中时用放宽模式和指令对齐找对应的指令再读，可信度降一级；起点依赖这一项自己的值（虚表槽号、命中位置上的偏移）的只在范围里搜索，所有这类依据都成立（槽里的函数还要和基线里的是同一个）的值恰好一个才采用。一项的所有依据必须给出同一个值。
- **位置无法确认的结论最多是需要人工**（B1）：命中位置没法对照、重新定位也没有指令对齐的确认（放宽的模式唯一命中但对齐有歧义，在要读的字段之后插入字段时它会命中后一个字段），这条依据的结论要有同一项里位置确认过的依据给出同样的值，否则这一项需要人工，原因写进 `report.txt`。
- 重新生成依据模式时先保住原模式的范围（原来在要读的指令前后各有几条，新模式也带上几条），保不住才退回最短的唯一模式并在报告里写明：U1 修复 FA 收紧的依据带着同一串复制和界标，退回最短模式会丢掉这层保护。
- **同组升级**（S4）：组里有 RUNTIME 项的值变了（或需要人工）、有特征码被重新定位（或需要人工）时，组里 NONE、OFFLINE 项改成需要人工，原因写明是哪个成员变了。
- 补丁先写进临时副本，在新 exe 上预演一遍 verify；预演不过（含误绑定、无法确认）的修复项改成需要人工、从补丁里拿掉，再预演，直到稳定。输出逐项报告（txt、json）、清单 diff、旧→新 RVA 对照表。`--apply` 只改清单文件（`--tree` 时改副本），然后自动再 verify；不把版本记为已知。

### 确认新版本：`accept`

已知版本在运行时不再停用只能离线核对、没有静态依据的项（ADR 0036），所以 accept 只接受运行时自己发现不了的问题都已经排除或人工确认过的版本（U1 修复 FB，审核 A 的 B2、S4、B1）：

| verify 里的结论 | accept |
| --- | --- |
| 必需项失效、误绑定 | 一律拒绝，先修 |
| 特征码只有静态检查不过（偷取范围、`DD_ENTRY` 等，运行时照样装 hook） | 一律拒绝，先修 |
| 离线依据不过（OFFLINE 项，或 RUNTIME 项上挂的离线检查） | 一律拒绝，先修（离线检查说值不对，不能靠确认放过） |
| 可选特征码失效（原因全是运行时也查的）、可选 RUNTIME 项的运行时依据不成立 | 加 `--allow-optional` 才接受（运行时自己会发现、停用依赖它们的能力） |
| 全部 NONE 项、同组升级的项、依据位置无法确认的项 | `--confirm <清单>` 逐项写核实方式（`method`）和证据路径（`evidence`，要存在）才接受；`--confirm-template <文件>` 生成要填的清单 |

拒绝信息只在失效全是运行时会自己发现的那类时才提 `--allow-optional`，其他情况写明要先修、`--allow-optional` 和 `--confirm` 都不管用。确认清单要写这个 exe 的 SHA1，接受时复制到基线目录的 `confirm/<版本名>.json`，和基线、`DD_KNOWN_BUILD` 一起进仓库，可以追溯是谁、按什么核实的。

「依据位置无法确认」允许人工确认（不是一律拒绝），原因是没有别的出路：一串同形状的字段里插入或删除一个时，按 token 本来就对不齐，人工把值和模式改对之后，位置核对拿旧基线比照样「没法对照」；新写的依据在旧基线里也没有参照。所以这类项和 NONE 项一样，靠人工核实、写下证据。默认（不带 `--confirm`）仍然拒绝。

### 什么时候一定报需要人工

修复工具遇到下面这些情况不给结论：模板孪生用调用图和字符串都区分不了（包括两份都有调用者、指纹和调用的目标都相同的情形）、没有调用者的函数被复制（虚函数）、生成不了唯一的特征码、hook 入口不安全（偷取范围里有分支或 rip 相对，换偷取方案要人定）、GLOBAL 的锚点或交叉检查有反证、值写在依据模式字面量里（`read=NONE`）的依据失效、虚表槽里换了函数时按固定槽号取函数的依据、一项的多条依据结论不一致、依据位置无法确认又没有佐证、只有离线依据的项（离线检查不给新值）、离线检查用新值不过、依据的锚点特征码没修好、同组有成员变了的 NONE/OFFLINE 项、预演 verify 不过。没有静态依据的项从来不修，列进「更新后要人工核实」，accept 时逐项确认。

### 自测：`dd_update.py selftest`

没有旧版本或新版本的 exe，自测靠两件事：Steam 版和离线版互相当作「更新前后」做盲定位（不用现有特征码，错误必须为 0），以及在 Steam 版的副本上模拟真实编译器输出的变异样本（函数搬迁、栈帧变化、模板孪生（没有调用者的、两份都有调用者的）、静默误绑定的诱饵、枚举表顺序、hook 入口不安全、虚表插入槽位、结构中间插入字段（`struct_shift`，以及审核 A 的两个反例：一串 int 字段里插入一个 `inst44`、删除一个 `inst_remove44`）、依据误绑定），逐个断言 verify 的结论和 repair 的结果，并检查不变式：修复项的新值等于真值，verify 判通过的项也真的对，新版本里不存在的字段不能给出任何值。结构里加字段的样本带上新字段完整的对应代码（复制、初始化、解析），函数原地变长、后面的函数依次后移（U1 修复 FB，审核 A 的 S7）。另外有清单变异冒烟、`repair --apply`/编译/`accept`（含确认清单）的往返、规则自检（对照测试的分类、加载器 GLOBAL、偷取字节、accept 的拦截）和 C++/Python 对照。样本说明和做不到真实的地方写在 `tools/ddupdate/mutants.py`。

## 和 ADR 0006、0036 的关系

- 补充 ADR 0006：地址仍然只用特征码，核心和可选特征码缺失时的降级不变；地址之外的布局进了清单，校验工具换成 `dd_update.py`，「误绑定」「无法确认」也算失效。
- ADR 0036 是这条流水线的运行时部分：DDCore 用同一份清单、同样的依据语义核对，未知版本的策略在那里。运行时不做的检查（HOOK 的静态检查、`DD_ENTRY`、依据位置核对、同组升级）只在 verify 里做，所以游戏更新后要先跑工具再发版；accept 的规则保证已知版本上运行时不再核对的项都核实过。

## 考虑过的方案

- 只看特征码唯一命中（ADR 0006 原来的做法）：发现不了误绑定，也发现不了结构偏移变化。
- 修复工具在第一名和第二名接近时选相似度高的那个：模板孪生里第一名和第二名常常完全相同，这样选就是猜；改成要求明显领先、否则报需要人工。
- 依据位置核对放进依据的求值语义（C++ 也做）：要在运行时带基线的指令序列和对齐算法，代价大；放在离线工具里，运行时只核对依据本身。
- 位置「没法对照」按通过处理（U1d 的做法）：审核 A 的 B1 反例证明它在最需要它的时候（一串同形状字段里插入、删除）恰好给出没法对照，verify 和 repair 都报通过、accept 把错值记成已知版本。改成不算通过。
- 只改进对齐、不改规则：同形状复制里多出的一对按 token 分不出是哪一对，任何对齐都只能如实给出歧义；改进对齐只减少本来就没有歧义的「没法对照」。
- `accept --allow-optional` 放行所有可选项失效（U1c 的做法）：OFFLINE 项失效时运行时不会发现，已知版本上照常按旧值用（审核 A 的 B2）。改成只放行运行时自己会发现的那类。
- 位置无法确认一律拒绝、不给人工确认：见上，人工改对以后照样没法对照，流水线会卡死。
- 基线存机器码：仓库是公开的，不存。
- 运行时自动采用读到的新值：不做，新值要经过修复工具和人工确认（ADR 0036）。

## 局限

- **同一性阈值和修复的区分力没有真实更新的数据**（审核 A 备注 8、10）：相似度数据（`build/u1a/simstats.txt`）里最近冒充者有 3 条高于阈值（`BuffLibraryIndex` 0.941、`FreeU32Vector` 1.0、`VectorDtor64` 1.0），`ActorDoAttackSkill` 的冒充者 0.804；「同一函数跨版本」只有同源的两个构建（最低 0.929）。盲定位「错误 0」只证明流程在这两个几乎一样的版本之间走得通，不能证明在真实更新上的区分力。缺的是一个真实的旧版本或新版本 exe（下载旧版要 Steam 账号，不在范围内）。
- 两个形状完全相同的小函数（取字段的 getter）互换槽位时指纹区分不了；模板孪生只能靠调用者和调用关系，对称时报需要人工。
- 只有离线依据和没有静态依据的项（枚举表、Effect 的大部分字段、事件负载、原型）变了只能报需要人工或靠自检发现；`instance_copy_fields`、`hero_stress_slot` 两个离线检查仍然只查「复制构造、槽 37 里出现过这个偏移」，它们挂的项另有运行时依据，这两个检查只是补充。
- 没有依据看的代码（例如按槽号调用虚函数的游戏代码）变了这套工具看不到。
- 每次 accept 都要逐项确认全部 NONE 项（现在 172 个，加上同组升级和无法确认的项）。确认清单可以引用同一份自检日志，但每项都要写，这是有意的成本：已知版本上运行时不再核对它们。

## 后果

- 游戏更新后的操作手册在 [06-workflow.md](../06-workflow.md)：verify → repair → 看报告和需要人工的项 → `--apply` → 构建 → 单元测试 → 测试目录自检 → 写确认清单 → `accept` → 用 RVA 对照表更新知识库 → `regen.sh --ghidra`。
- 插件作者用同一个工具校验和修复自己的特征码文件（`--sigs`），说明在 `templates/native/README.md`。
- 耗时：verify 每个 exe 约 20 秒，repair 每个 exe 1–2 分钟，selftest 全部约 40 分钟。
