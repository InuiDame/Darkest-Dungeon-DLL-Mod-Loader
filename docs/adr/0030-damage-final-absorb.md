# damage.final 在格挡判定处派发，吸收量可写

复刻 DDShield 需要护体和格挡之后的最终伤害，`damage.pre` 是护体之前的值。`damage.final` 挂在 `Actor::ConsumeHealthDamageBlock`（`480400`）入口，它的参数就是随后扣除的值（英雄的 `4836A0` 先算出最终伤害，再以它调用 `480400`）。字段：目标、攻击者（`480400` 的参数里没有，在外层槽位 50 的 detour 里记下，所以订阅 `damage.final` 时连同两个虚表 hook 一起装）、最终伤害、伤害类型、游戏是否已经格挡、是否在死门上、扣血前的生命，都只读；可写的是 `absorb`（0 到最终伤害，超出的夹到范围内）：

- 全部吸收：返回「已格挡」，游戏不扣血，显示 Blocked。
- 部分吸收：先把吸收量加回生命，游戏随后照常扣掉整个伤害，净损失是伤害减吸收量。只在游戏随后一定会扣血时补：英雄要不在死门上、生命不为 0（槽位 43、40 都为假）；怪物（`5FC3E0`）没有这两个判断，伤害不论大小都扣，只有免疫（`.can_be_damaged_directly` 为假且伤害类型在表 `DEB7D0` 里）时不扣，这时 `damage` 记 0、`absorb` 不起作用、游戏照常显示 immune；怪物生命已经不大于 0 时也不补。
- 怪物路径按 `480400` 的返回地址认（特征码 `MonsterBlockReturn`：返回点后面紧跟免疫判断，免疫表从同一个特征码解出）；英雄型怪物走英雄的 `4836A0`，按英雄处理。
- 游戏已经格挡时 `absorb` 不起作用；PvP 中不派发（[ADR 0011](0011-pvp-no-mutating-dispatch.md)）。主题名不以 `.pre` 结尾，能不能写由事件标志 `DD_EVENT_F_WRITABLE` 决定。

`480400` 也是 DDShield 的 hook 目标，DDCore 按 `DD_CHAIN_TARGET` 串联。

## 考虑过的方案

- 在 `damage.pre` 上吸收：那是护体之前的伤害，结算和 DDShield 不一致。
- 改 `480400` 的伤害参数：调用方把伤害留在自己的寄存器里（英雄的 xmm7），返回假之后扣的是它自己那份，改参数不影响扣血。
- 在 `4836A0`、`5FC3E0` 扣血的位置打补丁：函数中间的补丁，和 DDShield 的入口 hook 冲突的地方更多。
- 按槽位 50 记下的「是不是英雄」认怪物（审核 R2A-N1）：英雄型怪物的对象是 Monster 却走英雄的函数，要另外处理，没有离线覆盖，留到需要时。

## 后果

- 在死门上只有全部吸收能挡住这一击，部分吸收无效（补回就成了治疗）。
- 别的 native 插件经 `hook` 服务在 `480400` 上排在 DDCore 前面（priority ≤ 0）时，返回地址落在插件里，认不出怪物，写在 `dd_api.h`。
- 运行证据：P4a 的 `test_combat` 场景里英雄全部吸收时不掉血、用户看到 Blocked，部分吸收的净损失等于伤害减吸收量；P4 最终场景里怪物的部分吸收同样对得上（伤害 3、吸收 2、生命 8→7）。免疫怪物、死门上的吸收没有在游戏里跑过。
